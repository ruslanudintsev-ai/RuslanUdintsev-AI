# План безопасной публикации репозиториев для AI-портфолио

**Статус:** рабочий план, 29.10.2026. **Это не разрешение делать какие-либо приватные репозитории публичными.**

[Портфолио](../README.ru.md) · [Кейсы](../CASE_STUDIES.md) · [Правила доказательности](../EVIDENCE_AND_PRIVACY.md)

## Цель

Показывать будущим работодателям не количество проектов, а **полезные проверяемые результаты AI-assisted разработки**: постановку задач, управление агентами, PR/CI, тесты, работающие демонстрации и контроль выпусков. Каждый открытый проект должен усиливать портфолио. Сама публикация не является целью.

## Очерёдность

1. **Отбор.** Выбрать 3–5 проектов, затем по одному определить реальный статус: prototype / staging / production / paused. Отдельно зафиксировать роль владельца и роль coding agents.
2. **Аудит прав и безопасности.** Проверить право раскрывать исходники и сторонние зависимости, лицензию, конфигурацию, файлы и **всю историю Git**, теги, вложения и доступы. Удаление чувствительного файла из текущей версии не удаляет его из истории.
3. **Выбор формата.** При необходимости подготовить отдельную безопасную публичную демонстрацию или очищенную копию вместо переключения исходного рабочего репозитория в Public.
4. **Упаковка.** README должен объяснять задачу пользователя, возможности, стек, архитектуру, статус, быстрый запуск, тесты, ограничения, роль человека и агентов. Добавить только разрешённые изображения/демо и проверяемые ссылки.
5. **Верификация.** На конкретном SHA пройти тесты, CI, проверку документации, ссылок и воспроизводимости. Не путать PR, green CI, merge, deploy, индексацию, трафик и выручку.
6. **Решение владельца.** Запрашивать отдельное явное одобрение для каждого проекта, способа раскрытия и версии. До этого **никаких переключений видимости, зеркалирования или публикации исходников**.
7. **Публичная проверка.** После разрешённой публикации проверить видимость без авторизации, корректность README, отсутствие закрытых данных и работу демонстрации.
8. **Портфолио и резюме.** Добавить лучший подтверждённый кейс в [CASE_STUDIES.md](../CASE_STUDIES.md), обновить русскую/английскую навигацию и при необходимости закрепить репозиторий в профиле.

## Первые кандидаты на демонстрацию

- **KursoPilot** — AI-координация каталога, source-quality gates, выпуск и QA. Публичная ссылка на продукт не означает разрешения открыть его приватный исходный код. Релиз по отчёту оператора; независимый HTTP, индексирование и выручка требуют отдельной проверки.
- **PolisHelp** — развитие веб-продукта, практическая диагностика iPhone/HTTP2/Nginx и release QA. Уже есть [публичный технический кейс](https://github.com/ruslanudintsev-ai/ios-cellular-nginx-http2-fix).
- **AI-автоматизации** — небольшие воспроизводимые инструменты с документированными задачами, тестами и явными границами личной и агентной реализации.

Другие проекты рассматриваются только после фактического восстановления, проверки и отдельного разрешения. Работа агентов в чужих репозиториях не меняется этим планом.

## Шаблон кейса

**Проблема → роль владельца → вклад ИИ-агентов → критерии приёмки → доказательство (SHA/CI/демо) → результат → ограничения → статус.**

Не заявлять самостоятельную разработку всего кода, профессиональный опыт работы с технологиями только на основании агентной реализации или неподтверждённые коммерческие результаты. Не публиковать служебные, клиентские и личные данные.

## Критерий готовности к открытию

- [ ] Назначение и текущий статус проекта проверены.
- [ ] Отдельное разрешение владельца получено для точного проекта/версии.
- [ ] Права на публикацию и лицензии проверены.
- [ ] Вся история Git и материалы публикации проверены на чувствительные сведения.
- [ ] README, инструкции запуска, тесты и ссылки актуальны.
- [ ] Доказательства привязаны к конкретному окружению и SHA.
- [ ] Чётко разграничены работа человека и ИИ.
- [ ] Подготовлен план действий на случай обнаружения проблемы после публикации.

**Порядок:** качество и безопасность → демонстрация → подтверждение владельца → публикация → обновление резюме.
